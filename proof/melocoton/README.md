# Generated stubs checked in Melocoton

`camlid_custom.v` proves two stubs generated by camlid in
[Melocoton](https://github.com/logsem/melocoton) (Guéneau et al., OOPSLA
2023), a semantics of the OCaml FFI with a separation logic in Iris. The
goal is to check that the block model of `../spec.mlw` is not wrong: the
same rules (an unregistered `value` is lost at each allocation, a custom
block keeps its C memory) must hold in a semantics written by people who
know the OCaml runtime.

- `to_int` borrows the C value of a custom input and calls the C function;
- `two` initializes two C values, calls the C function, moves them into
  two new custom blocks and returns them in a tuple. The values are kept
  in `CAMLlocal` roots across the three allocations.

The C library and the templates of the type are hypotheses, written as
protocols (`lib_spec`). The stubs are translated by hand from the
generated C (in the comments); keep them in sync when the printer changes.
Not covered by Melocoton: finalizers (the C memory stays owned by its
foreign block), exceptions, `noalloc`, the release of the runtime lock.

## Setup

Melocoton needs Coq 8.16.1 and a fork of Iris, so it has its own switch:

    opam switch create melocoton ocaml-base-compiler.4.14.2 --no-switch
    opam repo add --this-switch --switch=melocoton coq-released https://coq.inria.fr/opam/released
    opam repo add --this-switch --switch=melocoton iris-dev git+https://gitlab.mpi-sws.org/iris/opam.git
    git clone https://github.com/logsem/melocoton ~/melocoton
    opam install --switch=melocoton --deps-only ~/melocoton/coq-melocoton.opam
    cd ~/melocoton && opam exec --switch=melocoton -- dune build @install

Tested on 2026-10-26 with Melocoton 039dae3 (2025-04-28). Then, from the
root of camlid: `make melocoton` (variables `MELOCOTON`,
`MELOCOTON_SWITCH`).
